## 0. 핵심 페르소나 & 설계 원칙

**대상 사용자:** 인터넷·모바일 조작에 익숙하지 않은 40-50대 학부모, 5개 반 중 1개에 배정

| 특성 | 영향 |
|------|------|
| 이메일 주소를 정확히 기억하지 못할 수 있음 | 에러 시 대안 경로(운영자 연락처) 필수 |
| 자신이 몇 반인지 확신하지 못할 수 있음 | 이메일 입력 후 반 정보를 명확히 보여주고 확인 절차 추가 |
| 모바일(스마트폰) 위주로 접속 | 터치 타겟 최소 44px, 코드 복사 버튼 필수 |
| 에러 메시지를 보면 불안해함 | 부정적 표현 최소화, 다음 행동 지시 항상 포함 |
| 카카오톡 인앱 브라우저로 접속하는 경우 많음 | 클립보드 API 폴백 처리 필요 |
| 세션 종료 후에도 코드를 잃어버릴 수 있음 | 기발급 코드 재확인은 세션 상태와 무관하게 동작 |

**UX 언어 원칙**
- 전문용어 금지 ("세션" → "강의", "서버 오류" → "일시적인 문제")
- 모든 오류 화면에 **다음 행동 지시** + **운영자 연락처** 포함
- 반 정보 표시 시 "○반" 뿐만 아니라 강의 예정 시각도 함께 표시

## 1. 기능 요구사항

### FR-01. 반 확인 (1단계)

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-01-01 | 사용자는 이메일 주소를 입력하여 자신의 소속 반을 확인할 수 있다 | 필수 |
| FR-01-02 | 이메일이 `members` DB에 존재하지 않으면 반 정보를 반환하지 않는다 | 필수 |
| FR-01-03 | 반 확인 결과에는 반 이름과 강의 예정 시각이 포함된다 | 필수 |
| FR-01-04 | 반 확인은 해당 반의 세션 활성 여부와 무관하게 동작한다 (언제든 내 반을 확인 가능) | 필수 |
| FR-01-05 | 이메일 형식 검증은 클라이언트와 API 양쪽에서 수행한다 | 필수 |
| FR-01-06 | 이메일 앞뒤·중간 공백은 클라이언트에서 제거 후 제출한다 | 필수 |

### FR-02. 코드 발급 (2단계)

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-02-01 | 반 확인 후 "맞아요, 코드 받기" 버튼을 눌러야 코드 발급이 시작된다 | 필수 |
| FR-02-02 | API는 발급 전에 회원 여부와 classId를 재검증한다 | 필수 |
| FR-02-03 | **기발급 확인을 세션 활성 확인보다 먼저 수행한다** (세션 종료 후에도 재확인 가능) | 필수 |
| FR-02-04 | 해당 반의 세션이 활성화되어 있지 않으면 코드를 발급하지 않는다 | 필수 |
| FR-02-05 | 동일 이메일로 이미 코드가 발급된 경우, 신규 발급 없이 기발급 코드와 반 정보를 반환한다 | 필수 |
| FR-02-06 | 동시 요청이 들어와도 1인 1코드를 보장한다 (Firestore 트랜잭션) | 필수 |
| FR-02-07 | 발급된 코드는 `LIVE-XXXXXXXX` 형식이며 혼동 문자(O, 0, I, 1, L)를 제외한다 | 필수 |
| FR-02-08 | 반 정보(classId)는 코드 문자열이 아닌 DB 필드로 관리한다 | 필수 |
| FR-02-09 | 반별 최대 발급 수량이 설정된 경우, 초과 시 발급을 거부한다 | 권장 |
| FR-02-10 | 발급 수량 카운터는 `issued_codes_meta/{classId}` 문서로 atomic 관리한다 | 권장 |
| FR-02-11 | fetch 요청에 타임아웃(10초)을 설정한다 | 권장 |

### FR-03. 세션 관리 (관리자)

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-03-01 | 관리자는 5개 반 각각의 세션을 독립적으로 시작/종료할 수 있다 | 필수 |
| FR-03-02 | 세션 시작/종료 시각을 각 반별로 기록한다 | 필수 |
| FR-03-03 | 관리자는 반별 최대 발급 수량을 설정할 수 있다 | 권장 |
| FR-03-04 | 관리자는 반별 강의 예정 시각(`scheduledAt`)을 설정할 수 있다 | 필수 |
| FR-03-05 | 관리자는 반별 운영자 연락처를 설정할 수 있다 (에러 화면 노출용) | 권장 |
| FR-03-06 | 관리자 페이지는 비인가 접근으로부터 보호된다 | 필수 |

### FR-04. 발급 내역 관리 (관리자)

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-04-01 | 관리자는 전체 또는 반별로 발급 내역을 조회할 수 있다 | 필수 |
| FR-04-02 | 목록에는 이메일, 코드, 반 이름, 발급 시각, 사용 여부가 표시된다 | 필수 |
| FR-04-03 | 관리자는 개별 코드를 무효화할 수 있다 | 권장 |
| FR-04-04 | 관리자는 특정 반 전체 코드를 일괄 무효화할 수 있다 | 권장 |
| FR-04-05 | 관리자는 반별 발급 내역을 CSV로 다운로드할 수 있다 | 선택 |

### FR-05. 코드 유효성

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-05-01 | 코드에는 유효기간이 존재할 수 있다 (미설정 시 무기한) | 선택 |
| FR-05-02 | 코드 사용 여부(`isUsed`)를 추적한다 | 권장 |
| FR-05-03 | 무효화된 코드는 사용 불가 처리된다 | 권장 |

### FR-06. 사용자 경험 (UX)

| ID | 요구사항 | 우선순위 |
|----|----------|----------|

## 2. 비기능 요구사항

### NFR-01. 성능

| ID | 요구사항 |
|----|----------|
| NFR-01-01 | 반 확인 API 응답 시간은 2초 이내여야 한다 |
| NFR-01-02 | 코드 발급 API 응답 시간은 3초 이내여야 한다 |
| NFR-01-03 | 클라이언트 fetch 타임아웃은 10초로 설정한다 |

### NFR-02. 보안

| ID | 요구사항 |
|----|----------|
| NFR-02-01 | 관리자 페이지는 인증 없이 접근할 수 없다 |
| NFR-02-02 | Firebase 서비스 계정 키는 서버 환경변수로만 관리한다 |
| NFR-02-03 | 이메일 입력값은 소문자 정규화 및 공백 제거 후 처리한다 |
| NFR-02-04 | API는 최소한의 에러 메시지만 반환한다 (DB 구조 노출 금지) |
| NFR-02-05 | API에서 이메일 형식을 정규표현식으로 검증한다 |

### NFR-03. 가용성

| ID | 요구사항 |
|----|----------|
| NFR-03-01 | Firebase 무료 티어(읽기 50,000건/일, 쓰기 20,000건/일) 내에서 5개 반 합산 운용 |
| NFR-03-02 | 반당 수십~수백 명 동시 요청을 처리할 수 있어야 한다 |

### NFR-04. 접근성 및 호환성

| ID | 요구사항 |
|----|----------|
| NFR-04-01 | 모든 텍스트는 WCAG AA 기준(대비 4.5:1 이상)을 충족한다 |
| NFR-04-02 | 코드 표시 폰트는 28px 이상으로 스크린샷 시 가독성을 보장한다 |
| NFR-04-03 | 터치 타겟(버튼, 링크) 최소 크기는 44×44px 이상이어야 한다 |
| NFR-04-04 | 카카오톡 인앱 브라우저, 구형 안드로이드 브라우저에서 핵심 기능이 동작해야 한다 |
| NFR-04-05 | 320px 이상의 화면 너비에서 코드가 한 줄로 표시되어야 한다 |

## 3. 제약 사항

| ID | 제약 |
|----|------|

## 4. 에러 케이스 정의

### 반 확인 단계 (1단계)

| 상황 | HTTP | 사용자 친화 메시지 | 후속 지시 |
|------|------|--------------------|----------|
| 이메일 형식 오류 | 400 | "이메일 주소를 정확히 입력해 주세요." | "예시: 홍길동@naver.com" |
| 미가입 이메일 (1-2회) | 404 | "입력하신 이메일로 등록된 정보를 찾을 수 없습니다." | 힌트 제공 |
| 미가입 이메일 (3회+) | 404 | 위 동일 | 운영자 연락처 강조 |
| 서버/네트워크 오류 | 500 | "일시적인 문제가 생겼습니다." | 재시도 버튼 + 연락처 |

### 코드 발급 단계 (2단계)

| 상황 | HTTP | 사용자 친화 메시지 | 후속 지시 |
|------|------|--------------------|----------|
| 이미 발급됨 | 200 | "이전에 발급받으신 코드입니다. 그대로 사용하시면 됩니다." | 코드 재노출 + 복사 버튼 |
| 반 세션 비활성 (시작 전) | 403 | "아직 강의가 시작되지 않았습니다." | scheduledAt 안내 + 강사 안내 대기 |
| 반 세션 비활성 (종료 후) | 403 | "코드 발급이 종료되었습니다." | 강사 직접 문의 + 연락처 |
| 수량 소진 | 403 | "준비된 코드가 모두 소진되었습니다." | 강사 직접 문의 + 연락처 |
| 서버/네트워크 오류 | 500 | "일시적인 문제가 생겼습니다." | 재시도 버튼 + 연락처 |

## 5. 엣지케이스 목록

### 5-1. v0.1~0.3 기존 엣지케이스

| EC# | 시나리오 | 심각도 | 조치 |
|-----|----------|--------|------|
| EC-01 | 가입 이메일 오기억 | 높음 | 에러 힌트 + 연락처 |
| EC-02 | 이메일 중간 공백 삽입 | 높음 | 클라이언트 공백 제거 |
| EC-03 | 도메인 모르고 순차 시도 | 중간 | 3회 실패 시 연락처 강조 |
| EC-04 | 자동완성이 엉뚱한 이메일 입력 | 높음 | 반 확인 단계에서 이메일 재표시 |
| EC-05 | 모바일 데이터 불안정 | 높음 | AbortController 타임아웃 10초 |
| EC-06 | 코드 화면 닫아 분실 | 높음 | 복사 버튼 + 재확인 안내 |
| EC-07 | 야외 스크린샷 가독성 | 중간 | WCAG AA 대비, 28px 이상 |
| EC-08 | 라이브 시작 전 접속 | 높음 | scheduledAt 표시, "곧 시작" 안내 |
| EC-09 | 세션 종료 후 코드 재확인 불가 | 긴급 | 기발급 확인을 세션 체크보다 먼저 |
| EC-10 | 강사가 실수로 세션 껐다 재개 | 중간 | 재시도 버튼 |
| EC-11 | 부부가 같은 계정으로 각자 시도 | 중간 | "같은 이메일은 하나의 코드만" 안내 |
| EC-12 | 자신의 반이 맞는지 확신 못함 | 높음 | 반 확인 단계 "이 반이 맞아요 / 아닌 것 같아요" 선택 |
| EC-13 | 수량 소진 체크 미구현 | 긴급 | 카운터 문서 기반 atomic 체크 |
| EC-14 | Firebase 환경변수 누락 시 500 | 높음 | error.tsx 글로벌 에러 페이지 |
| EC-15 | Firestore 느릴 때 버튼 여러 번 탭 | 높음 | 스피너 + disabled 강화 |
| EC-16 | API 이메일 형식 검증 없음 | 높음 | 정규표현식 검증 추가 |
| EC-17 | 카카오 인앱 브라우저 클립보드 실패 | 중간 | readonly input 폴백 |
| EC-18 | 성공 후 다른 이메일로 재발급 방법 없음 | 낮음 | "다른 이메일로 받기" 링크 |
| EC-19 | 320px 구형폰 코드 줄바꿈 | 중간 | whitespace-nowrap |
| EC-20 | 어느 강의인지 맥락 불명 | 중간 | 반 이름 + 강의 시각 표시 |

### 5-2. v0.4 신규 엣지케이스 (2단계 플로우 + 5반 구조 시뮬레이션)

| EC# | 시나리오 | 심각도 | 카테고리 | 대응 방안 |
|-----|----------|--------|----------|----------|
| EC-N01 | `members`에 `classId` 필드 누락 | 🔴 긴급 | 데이터 | API에서 명시 처리 → "반 배정이 완료되지 않았습니다" 안내 |
| EC-N02 | `classId`는 있는데 `classes` 문서 없음 (orphaned) | 🔴 긴급 | 데이터 | `!classDoc.exists` 처리 → EC-N01과 동일 에러 화면 |
| EC-N03 | DB에는 1반인데 본인은 다른 반이라고 알고 있음 | 🟢 낮음 | 데이터 | SCR-ERR-G에 "이메일·조회된 반"을 함께 표시해 운영자가 전화로 빠르게 대응 |
| EC-N04 | "맞아요" 버튼 대신 "아닌 것 같아요" 링크를 오클릭 | 🟠 높음 | UX | SCR-ERR-G에 "돌아가서 코드 받기" 버튼 추가. 링크와 버튼 간격 24px 이상 확보 |
| EC-N05 | SCR-01B 확인 중 세션 ON→OFF 전환 | 🟢 낮음 | UX | SCR-ERR-C에 "잠시 후 다시 시도" 버튼 추가 |
| EC-N06 | 앱 전환 후 돌아오면 이메일 입력값 소실 | 🟡 중간 | UX | `sessionStorage`에 마지막 조회 이메일 저장, 재진입 시 자동 복원 |
| EC-N07 | SCR-01B 비활성 상태에서 반복 클릭 | 🟡 중간 | UX | 세션 비활성 시 버튼 텍스트 "강의 시작 후 코드 받기"로 변경. 선택적 자동 재시도 카운트다운 |
| EC-N08 | `issue-code` API에 `classId` 클라이언트 주입 | 🔴 긴급 | 보안 | API 내부에서 `members/{email}` 직접 조회로 classId 결정. 클라이언트 입력 `classId` 무시 |
| EC-N09 | `check-member` API로 이메일 대량 탐색 | 🟡 중간 | 보안 | IP 기반 rate limiting (동일 IP 10초 내 5회 초과 시 차단) |
| EC-N10 | 관리자가 잘못된 반의 세션을 켜는 실수 | 🟠 높음 | 운영 | 세션 시작/종료 버튼 클릭 시 "X반 라이브를 시작하시겠습니까?" 확인 모달 필수 |

| EC-N12 | 여러 반이 동시 활성화된 상태를 관리자가 인지 못함 | 🟡 중간 | 운영 | 대시보드 상단에 "현재 활성 반: N개" 배너. 2개 이상 시 주황 경고 |
| EC-N13 | 옆 사람은 코드 받는데 나는 "시작 안됨" (다른 반) | 🟠 높음 | UX | SCR-ERR-B 메시지에 반 이름 포함: "3반 강의가 아직 시작되지 않았습니다" |
| EC-N14 | 동일 이메일이 여러 반에 중복 등록 | 🔴 긴급 | 데이터 | `members` 컬렉션의 문서 ID를 이메일로 설정 (issued_codes와 동일 방식) |
| EC-N15 | check-member↔issue-code 사이 반 배정 변경 | 🟢 낮음 | 데이터 | `issue-code` 응답에 실제 발급된 반 이름 포함 → SCR-02에서 재확인 가능 |

## 6. 데이터 모델

### `classes` 컬렉션
```
{
  // 문서 ID = "class-1" ~ "class-5"
  name: string,              // 표시 이름 (예: "1반", "오전반")
  scheduledAt: Timestamp,    // 강의 예정 시작 시각
  isActive: boolean,
  maxCodes?: number,
  instructorContact?: string,
  startedAt?: Timestamp,
  endedAt?: Timestamp
}
```

### `members` 컬렉션
```
{
  email: string,    // 소문자 정규화
  classId: string,  // 예: "class-3"
  name?: string,
  joinedAt: Timestamp
}
```

### `issued_codes` 컬렉션
```
{
  // 문서 ID = 이메일 (소문자)
  email: string,
  classId: string,
  code: string,       // LIVE-XXXXXXXX
  issuedAt: Timestamp,
  isUsed: boolean,
  usedAt?: Timestamp,
  isRevoked?: boolean
}
```

### `issued_codes_meta/{classId}` 문서
```
{
  total: number  // 반별 발급 총 건수
}
```

## 7. 용어 정의

| 용어 | 정의 |
|------|------|
| 반 (class) | 동일 강의를 서로 다른 시간에 수강하는 그룹. 5개 반이 존재 |
| 반 세션 | 관리자가 특정 반에 대해 활성화한 코드 발급 가능 구간 |
| 코드 | `LIVE-XXXXXXXX` 형식의 고유한 문자열 (반별로 서로 다름) |
| 기존 가입자 | `members` 컬렉션에 이메일과 classId가 등록된 사용자 |
| 반 확인 | 이메일 입력 후 소속 반 정보를 조회하는 1단계 |
| 기발급 재확인 | 이미 발급된 코드를 세션 상태와 무관하게 다시 반환하는 동작 |
